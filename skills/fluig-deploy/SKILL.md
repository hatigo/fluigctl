# Publishing to a Fluig server

This skill ships inside the `fluigctl` repository, so the commands here and the
installed CLI are the same version. To put it where agents look for it:

```sh
fluigctl skill install
```

`fluigctl` publishes datasets, forms, widgets, WCM layouts, global events,
attribution mechanisms, whole process diagrams and the workflow scripts of an
existing process from a Fluig workspace, and pulls each of them back. It replaces
clicking through Fluig Studio or the Fluiggers VS Code extension, and it is the
only sanctioned way to publish from a session.

Writing the artifact is a different job; this skill only publishes what is in the
repository.

## Before the first push of a session

```sh
fluigctl server ls
```

Registering servers is the human's job. Point them at the screen, which is
guided and checks each credential before writing it:

```sh
fluigctl server ui
```

It needs a real terminal, so it refuses from a session (exit 5) — do not try to
drive it, and do not add or remove servers behind the human's back.

No servers, or the one you need is missing:

```sh
fluigctl server import ~/fluig/workspaces          # shows what it would import
fluigctl server import ~/fluig/workspaces --write  # writes
```

Import reads the extension's `.vscode/servers.json` files. With
`--with-passwords` it also decrypts each password (with this machine's VS Code
key) and copies it into fluigctl's own env file — the CLI does it, the value is
never printed:

```sh
fluigctl server import ~/fluig/workspaces --with-passwords          # shows what it would copy
fluigctl server import ~/fluig/workspaces --write --with-passwords  # copies
```

The password never lives in the config. `fluigctl` looks for it, in order, in
the environment variable named there, its own env file, and the
`.vscode/servers.json` of the current folder or above — always the CLI, not
you. Never read, print or echo that value, never open a file holding it, and
never decrypt `servers.json` yourself. If no source has it, the command names
all three; that is a question for the human, not something to work around.

Whenever fluigctl uses a `servers.json` it adds `.vscode/servers.json` to that
repository's `.gitignore`. If it warns the file is already **versioned**, tell
the human: ignoring it does not remove it from history.

## What to publish

```sh
fluigctl changed --server <servidor>                # working tree
fluigctl changed --since main --server <servidor>   # since a ref
```

It reads git, maps changed files to artifacts and prints one `--dry-run`
command per artifact, suggesting `--new-version` for a form whose HTML gained a
field. It covers datasets, forms, widgets, WCM layouts, global events
(`events/`), mechanisms (`mechanisms/`) and process diagrams. For a changed `.process` it suggests `push diagram`, which also publishes
that process's scripts — do not add a separate `push process` for them, it would
create another version on top. Files under `workflow/.resources` are generated by
Studio and are only listed. It sends nothing. Publish artifact by artifact, never
in a batch.

## Showing a diagram while you work

When the human asks to see or follow changes to a `.process`, start the local
viewer for that exact file:

```sh
fluigctl diagram open workflow/diagrams/<processo>.process
```

The command opens the browser even when an agent invokes it, then returns
immediately while the viewer stays in the background. Do not add `--no-open`
when the human asked to see it. The drawing updates whenever you write a valid
`.process`; an invalid intermediate write leaves the last valid drawing visible
and shows the error. Running `open` again reuses the same viewer. The human can
click or keyboard-select pools, lanes, activities, events, gateways, flows and
artifacts to inspect friendly properties. Selection follows the same object ID
across your writes; XML serialization blobs from Studio are deliberately not
shown or sent to the browser.

The URL contains a local access token. It is safe to show to the human in this
session, but do not publish it in logs, issues or commits. When they ask to stop:

```sh
fluigctl diagram close workflow/diagrams/<processo>.process
```

This viewer is read-only. Do not claim that the human can edit the diagram in
this first version.

## Pushing

Always dry-run first against a server you have not pushed to in this session.
It resolves the target and prints it without sending anything.

```sh
fluigctl push dataset datasets/dsFoo.js --server <servidor> --dry-run
fluigctl push dataset datasets/dsFoo.js --server <servidor>
```

A dataset that does not exist on the server is refused; add `--create` and
`--description` only when creating one is actually intended.

Forms **must** state what happens to the version — there is no default:

```sh
fluigctl push form forms/formFoo --server <servidor> --keep-version   # overwrite in place
fluigctl push form forms/formFoo --server <servidor> --new-version    # next version, previous stays readable
```

The target form is resolved by `--document-id`, then the folder's numeric
prefix, then the Fluig Studio `.metadata` in the folder (the documentId of each
past export, checked against the server), then the folder name. The folder name
lies — `forms/formReembolso` is document 902 on the Cetenco HML, and the form
named `formReembolso` (676) is a different one. Read every `aviso:` line of the
dry-run, and if the target is not the form the process uses, stop and pass
`--document-id`.

An update keeps the server's form name and descriptor field; the dry-run prints
both. Change them only on purpose, with `--description` / `--description-field`.

A dataset update keeps the server's description, saves the previous code under
`~/.local/state/fluigctl/backups/` and checks afterwards that the server returns
the local code (exit 7 if not). The dry-run says when the server already has it.

Creating a form needs three things that cannot be guessed, and
`persistenceType` cannot be changed afterwards:

```sh
fluigctl push form forms/formNovo --server <servidor> \
  --create --parent-id <pasta> --dataset-name dsformNovo --persistence-type form
```

A process push publishes only the scripts in `workflow/scripts/` into a process
that already exists on the server. Like Studio, the script prefix is the name of
the `.process` file whose id is the given process id (they differ when a process
was renamed); without such a file, the id itself. The diagram, activities and
assignments go through `push diagram`; a process missing on the server is
refused (exit 3). It creates a new version and releases it unless you pass
`--no-release`:

```sh
fluigctl push process <processId> --server <servidor> --dry-run
fluigctl push process <processId> --server <servidor> [--no-release]
```

A diagram push publishes the whole `.process` (diagram, activities,
assignments, scripts and the diagram image). `--create` creates a process that
does not exist yet. **A diagram is never published or republished without a
form**: an empty `cardIndex` is refused (exit 6), even in `--dry-run` — link the
form in Studio or set `cardIndex` to the documentId of a form on the server.

The converter covers pool, lane, group, start, user, service, script and e-mail
tasks, the four gateways, intermediate events (timer, conditional, signal, error
and link), subprocess (common and ad hoc), annotation, document, database, flows
and bends, descriptor fields, application configuration, attachment rules and
attachment security, and extended properties. Of the 95 `.process` files in a
real set of workspaces, all 95 convert.

What it still refuses is what the format cannot express or the server will not
release, with exit 6 before any network call and naming the reason:

- a mechanism named on a gateway branch with no configuration — the server
  answers "possui um mecanismo que não foi configurado" at release, so the
  diagram is incomplete in Studio too
- a script file whose name is not `<arquivo>.<evento>.js` for that process
- a flow with neither a source nor a target, or a condition pointing at a state
  the gateway has no flow to

Do not edit the `.process` to get around a refusal: it lists what is missing, and
the answer is usually Studio. A subprocess calls another process by id: the target
must already exist on the destination server. The volume and the business periods
(expedientes) named in the `.process` must also exist there, or the push stops
with exit 6 before writing — register them in the destination's control panel or
fix the diagram in Studio. The category is free text and is not checked.

```sh
fluigctl push diagram workflow/diagrams/<processo>.process --server <servidor> --dry-run
fluigctl push diagram workflow/diagrams/<processo>.process --server <servidor>
```

Read the publish result: `ok=true` with `activityError=[]` and `flowError=[]`
means the new version was released cleanly. To check that a process actually
runs, open and move a request through
`POST /process-management/api/v2/processes/<id>/start` and
`POST /process-management/api/v2/requests/<n>/move` (body: `movementSequence`
of the open task, `assignee`, `targetState` = the numeric suffix of the target's
id in the `.process`, optional `formFields`), from a session logged into the
portal — only on a homolog server and only when the user asked for it. The
fluigctl README has a full worked example (the test process, with a user task,
a service task and a gateway). A released version cannot be removed through the
API and a request can only be cancelled, never deleted: publishing a throwaway
process leaves it on the server until someone removes it in the portal.

A widget push takes the widget folder, packs the `.war` in memory as the
Fluiggers extension does, and sends it. There is no `--create`: the server
installs or updates.

```sh
fluigctl push widget wcm/widget/<nome> --server <servidor> --dry-run
fluigctl push widget wcm/widget/<nome> --server <servidor>
```

Installation is asynchronous — success means the server accepted the `.war`,
not that the widget is live. To verify, fetch
`/<context-root>/resources/js/<nome>.js` from the server and compare it with
the local file. A folder that is not a widget, or a symlink, is refused with
exit 3.

**The target is the `application.code` in `src/main/resources/application.info`,
not the folder name and not the `.war` file name.** A package sent as
`DSA001semClasses.war` was registered as `DSA_001_java_gestao_contrato`. The push
names the war after the code and warns when the folder disagrees; without
`application.code` it refuses (exit 3) before the network.

**A widget with files in `src/main/java` cannot be published at all, and it is
not a matter of compiling.** The WCM upload route refuses any `.war` carrying
Java — loose class, renamed package, classes inside a `.jar`, or with the
`Dependencies` manifest the Maven build declares — answering `500 Existe uma
declaração de componente repetida na lista de recursos da widget`. The same
package without the classes goes up with 200. `fluigctl` refuses with exit 6
before sending; publish that widget through Studio, and do not "fix" it by
dropping the classes, which would upload a version without its Java, silently.

A WCM layout is the same kind of application, and goes up by the same route:

```sh
fluigctl push layout wcm/layout/<nome> --server <servidor> --dry-run
fluigctl push layout wcm/layout/<nome> --server <servidor>
```

What separates a widget from a layout is `application.type` in the same
`application.info`, and each command requires its own: a layout sent by
`push widget` would install a layout as a widget, and the server accepts it. The
wrong command is refused with exit 6, naming the right one.

Global events and attribution mechanisms are JavaScript published over REST, not
through Studio:

```sh
fluigctl push event events/<eventId>.js --server <servidor> --dry-run
fluigctl push mechanism mechanisms/<id>.js --server <servidor> --dry-run
```

**The global-event route replaces the whole list on the server.** Sending one
event deletes the others, so `fluigctl` reads the list, swaps its entry and sends
the list back — and a read that fails is refused rather than becoming an empty
list, which would wipe every event on the client's server. Both commands verify
by re-reading. A mechanism that does not exist needs `--create`; without it the
push refuses (exit 6). On update, `name`, `description`, `controlClass`,
`assignmentType` and `configurationClass` come from the server, not from the
file — `--name` and `--description` are the only overrides. The server compiles a
global event on write, and a syntax error comes back with the event name and the
line.

## Pulling from a server

When someone published straight to the server and the repository is behind,
bring it back instead of copying code from the portal:

```sh
fluigctl pull process <processId> --server <servidor> --dry-run
fluigctl pull dataset <nome> --server <servidor> --dry-run
fluigctl pull diagram <processId> --server <servidor> --dry-run
fluigctl pull form forms/formFoo --server <servidor> --dry-run
fluigctl pull widget <code> --server <servidor> --dry-run
fluigctl pull event [<eventId>] --server <servidor> --dry-run
fluigctl pull mechanism [<id>] --server <servidor> --dry-run
```

`pull process` writes each event of the published definition to
`workflow/scripts/<prefixo>.<evento>.js`, with the same prefix as `push process`.
`pull dataset` writes to the existing `datasets/**/<nome>.js`, or
`datasets/<nome>.js`; factory datasets (`BUILTIN`) and two local files with the
name are refused (exit 6). `pull diagram` converts the published definition back
into `workflow/diagrams/<id>.process`, covering states, assignments, gateways,
events, subprocesses, extended properties, form fields, attachment rules,
graphical components, lanes, flows and bends. It refuses (exit 6) a definition
carrying data the `.process` cannot represent — an error event bound to a state
that does not exist, or a terminal end event with `notifyAuthorityDelay=true`.
That refusal is deliberate: Studio would silently drop the event or write
`false`, so publishing after a pull would change the process.

`pull event` and `pull mechanism` write the files `push event` and
`push mechanism` read; without an id they bring every one the server has. The
name and description of a mechanism stay on the server, so the push preserves
them from there.

`pull widget` needs the Fluiggers helper widget installed on the server, because
Fluig has no route to download an installed widget. Without it the command
refuses with exit 3 and points at `--instalar-helper`, which **publishes that
helper on the client's server** — third-party code, and a write. Ask the human
before using it; it does not work with `--dry-run`, by design. The pulled tree
drops nothing silently: entries with no place in the folder are listed, and a
widget with Java comes back with its classes in `src/main/java`, which the push
will then refuse — that pair does not round-trip, and Studio is the way back.

`pull layout` does not exist: Fluig exposes no route to list or download
layouts. The helper queries `WHERE APPLICATION_TYPE = 'widget'`, and layouts,
though in the same table, are out of its reach.

A local file that differs from the server is never replaced silently: without
`--overwrite` nothing is written and it exits 6 listing the files. Show the human
the difference before adding `--overwrite` — the local one may be unpublished
work.

## Production is the human's

A server marked `prod` requires the password typed at a terminal. A session has
no terminal, so the push will fail with exit 5 — that is the design, not an
obstacle to route around.

When the target is production: stop, and give the human the exact command to
run themselves. Never suggest unmarking the server, and never look for another
path to the same write.

## Exit codes

| | |
|---|---|
| 0 | done |
| 2 | bad usage, including a form push with no version choice |
| 3 | server or file not found |
| 4 | password variable unset or refused |
| 5 | needs a human at a terminal — the production gate, and `server ui` |
| 6 | ambiguous or missing match; the message names the flag that resolves it |
| 7 | the Fluig server refused the operation |

Codes 2 to 6 are decided before anything is sent, so nothing was written. Code
7 means the server was called and refused. Report the message as it came; do
not retry with different flags hoping one sticks.

## What the server enforces

Measured against Fluig 1.8, and the reason several pushes fail before sending:

- a `fileName` with a subfolder is rejected, so `fluigctl` sends each attachment by its file name alone, as the Fluiggers extension does; the published form still resolves `libs/x.js`. Two files sharing a name in different folders are refused (exit 6)
- the main HTML needs a `<form>` tag
- `events/*.js` become form events; `.metadata` is never published
- `addDataset` on an existing name is refused, so `--create` by mistake is safe
- a dataset update without `--description` preserves the one on the server
- the WCM upload route refuses any `.war` with Java, whatever shape it takes
- the global-event route replaces the whole list, so it is read-modify-write
- the server identifies a WCM application by `application.code`, not by the file
  name; a widget is registered under that code

## Never

- Never push to production from a session, and never try to drive `server ui`.
- Never run `pull widget --instalar-helper` without asking: it publishes a
  third-party widget on the client's server.
- Never publish a global event without knowing that the route replaces the whole
  list on the server.
- Never read the password variable, or a file holding it.
- Never push without a dry-run when the target server is new to this session.
- Never pass a password on the command line or in an environment variable you
  set yourself; if fluigctl cannot find it, ask the human.
